# 委派评审：哪些委派真的会在宿主那边生效

> **问题**：我们把 12 条约束委派给了 eslint / stylelint / knip 等生态工具（`docs/DESIGN.md` §4.9）。
> 但**"生态有这条规则" ≠ "宿主会开它"** —— 宿主没装、没配、没跑，那一整类就是**零覆盖**。
> 这份评审逐条估"开启可能性"，并把"开启成本高但我们兜得起"的那几条挑出来。
>
> 结论先看 §2；要动手的清单在 §5（**要你点头**）。

## 1. 判据：三个门槛 + 一档成本

委派要真的生效，宿主得连过三关：

| 门槛          | 意思                         | 怎么估                                |
| ------------- | ---------------------------- | ------------------------------------- |
| **G1 装了没** | 工具在 `devDependencies` 里  | 生态规模（周下载量）+ 项目类型        |
| **G2 配了没** | 规则在 config 里且不是 `off` | **默认开？还是要逐条写配置？** ← 关键 |
| **G3 跑没跑** | 在提交链路 / CI 里真的执行   | 只有 R-51 能查                        |

**开启成本三档**（决定 G2）：

- **A 开箱即用**：主流 preset 里默认就是 error/warn（装了就等于开了）
- **B 一行配置**：默认 `off`，认真项目会加一行
- **C 要写自定义配置**：要写 AST 选择器 / 属性值白名单 / 装专门工具并接线 —— **多数项目不会写**

**一个真实的参照**：本仓自己的 `eslint.config.mjs` 开了 `no-explicit-any` · `ban-ts-comment` · `no-empty` ·
`no-warning-comments` · `max-lines` · `max-lines-per-function` · `no-console`；
**没开** `no-restricted-syntax`（假异步 / 随机 / 硬编码地址 / 假数据）· `no-restricted-imports`（`../` 越级）·
`complexity` / `max-depth` / `max-params`。连一个天天写门禁的仓库都是这个分布。

## 3. 三条观察

1. **"生态没有"不是主要风险，"生态有但没人配"才是。** A 档（开箱即用）只有两条；C 档（要写自定义配置）
   有六条 —— 而 C 档恰恰是"项目最需要、也最容易漏"的那类约束。
2. **我们最擅长的正好是"配置成本"这件事**：委派不牢的那几条，都是需要项目写一份**声明**
   （哪些形态、哪些落点、哪些白名单）的；而这正是本体的机制（声明 + 数据表 + 零误伤）。
   换句话说：**越需要逐项目声明的约束，越不该委派** —— 委派清单现在的判据只看了"纯语法/纯图属性"。
3. **三条已经在本体里判过的（S08 / S15 / S16）本来就该留**：委派出去不是"省事"，而是"少一层覆盖"。
   同理，**P03/P08 的事实早就读进来了**（`--verify-deps` 用的就是它），却没人在判 —— 这是最明显的缺口。

## 4. 判据的修订建议

`docs/DESIGN.md` §4.9 现在的判据是「纯语法 / 纯图属性、且不需要项目专有数据 → 委派」。
建议补两条，把"配置成本"和"漏掉的代价"纳入：

> **委派的三个条件（缺一不可）**：
> ① 纯语法 / 纯图属性，不需要项目专有数据；
> ② **宿主不写自定义配置就能生效**（否则那条约束实际等于没人管）；
> ③ 本体没有现成事实可直接判定（有的话自己判更稳，边际成本接近 0）。
>
> 委派之后仍然要能回答"它到底跑没跑"（R-51）。

## 5. 建议动作（要你点头才动手）

| #     | 动作                                                                                                                               | 代价                            | 收益                                                          |
| ----- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------- |
| **A** | **收回 P03 / P08**：幽灵依赖、声明了没用的依赖 → 本体实现（事实 `ctx.deps.phantom` / `unused` 早就算好，`--verify-deps` 一直在用） | 两条规则 + 夹具                 | 补上一个现在**完全没人管**的缺口                              |
| **B** | **样式三条兜底**：颜色字面量（D01）、`!important`（D09）、数值白名单（D12–D14）→ 本体实现，**默认关、声明才判**                    | CSS 扫描器已有，三条规则 + 夹具 | stylelint 的这三项配置成本最高，兜底后不装 stylelint 也有覆盖 |
| **C** | **形态型兜底**：假异步 / 随机 / 硬编码地址 / 假数据（H07–H09）→ 本体实现，形态由项目声明（或走数据表 + `allowOwn` 放宽）           | 两条规则 + 夹具 + 声明字段      | 覆盖"要写 AST 选择器才有人管"的那一类                         |
| **D** | **相对越级 `../`（S10）或 TODO（H04）挑一条**顺手收回                                                                              | 各一条规则                      | 极便宜，但生态也便宜 —— 优先级最低                            |

**不建议动的**：`any` / 空 catch / console（开箱即用或一行配置，重写只会与生态重复）、
S08 / S15 / S16（本体已经在判，委派只是补充）。

**同时建议加一条门禁（就是 R-51）**：读宿主的 `devDependencies` 与 lint 链路，回答
"我们声明委派出去的那 N 条，到底有没有对应的工具在跑" —— 没有就明说"这 N 类零覆盖"。
没有它，这份评审的结论只能靠猜（G3 那一栏现在是空的）。

## Comments

- 2026-09-25 用户提出："哪些委派出去了用户开启可能性比较大？开启可能性小的我们自己支持也不是不行。"
  这份评审给出的答案是：**按"开启成本"分档，C 档（要写自定义配置）的六条里，四条建议本体兜底**；
  并把判据从两条（纯语法 / 不需要项目数据）扩到三条（+ 宿主不写配置就能生效 + 本体没有现成事实）。
- 依据的生态规模来自 `docs/ALTERNATIVES.md`（2026-09 的周下载量）：knip 10.4M · dc 2.9M ·
  i18next 插件 1.0M · stylelint 值白名单 383K —— 装机规模都不小，但**规则是否开启**是另一回事。
