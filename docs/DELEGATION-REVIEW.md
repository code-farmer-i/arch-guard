# 委派评审：哪些委派真的会在宿主那边生效

> **问题**：我们把 12 条约束委派给了 eslint / stylelint / knip 等生态工具（`docs/DESIGN.md` §4.9）。
> 但**"生态有这条规则" ≠ "宿主会开它"** —— 宿主没装、没配、没跑，那一整类就是**零覆盖**。
> 这份评审逐条估"开启可能性"，并把"开启成本高但我们兜得起"的那几条挑出来。
>
> 结论先看 §2；要动手的清单在 §5（**要你点头**）。

## 1. 判据：三个门槛 + 一档成本

委派要真的生效，宿主得连过三关：

| 门槛          | 意思                         | 怎么估                                |
| ------------- | ---------------------------- | ------------------------------------- |
| **G1 装了没** | 工具在 `devDependencies` 里  | 生态规模（周下载量）+ 项目类型        |
| **G2 配了没** | 规则在 config 里且不是 `off` | **默认开？还是要逐条写配置？** ← 关键 |
| **G3 跑没跑** | 在提交链路 / CI 里真的执行   | 只有 R-51 能查                        |

**开启成本三档**（决定 G2）：

- **A 开箱即用**：主流 preset 里默认就是 error/warn（装了就等于开了）
- **B 一行配置**：默认 `off`，认真项目会加一行
- **C 要写自定义配置**：要写 AST 选择器 / 属性值白名单 / 装专门工具并接线 —— **多数项目不会写**

**一个真实的参照**：本仓自己的 `eslint.config.mjs` 开了 `no-explicit-any` · `ban-ts-comment` · `no-empty` ·
`no-warning-comments` · `max-lines` · `max-lines-per-function` · `no-console`；
**没开** `no-restricted-syntax`（假异步 / 随机 / 硬编码地址 / 假数据）· `no-restricted-imports`（`../` 越级）·
`complexity` / `max-depth` / `max-params`。连一个天天写门禁的仓库都是这个分布。

## 3. 三条观察

1. **"生态没有"不是主要风险，"生态有但没人配"才是。** A 档（开箱即用）只有两条；C 档（要写自定义配置）
   有六条 —— 而 C 档恰恰是"项目最需要、也最容易漏"的那类约束。
2. **我们最擅长的正好是"配置成本"这件事**：委派不牢的那几条，都是需要项目写一份**声明**
   （哪些形态、哪些落点、哪些白名单）的；而这正是本体的机制（声明 + 数据表 + 零误伤）。
   换句话说：**越需要逐项目声明的约束，越不该委派** —— 委派清单现在的判据只看了"纯语法/纯图属性"。
3. **三条已经在本体里判过的（S08 / S15 / S16）本来就该留**：委派出去不是"省事"，而是"少一层覆盖"。
   同理，**P03/P08 的事实早就读进来了**（`--verify-deps` 用的就是它），却没人在判 —— 这是最明显的缺口。
4. **依赖两条要拆开看**：
   - **幽灵依赖（P03）** 确实有广装机方案（`eslint-plugin-import` 的 `no-extraneous-dependencies`），
     但它**不在任何 recommended 里、要显式开**，而且得先装那个插件 ——
     **本仓就是一个反例：`devDependencies` 里只有 `eslint` + `typescript-eslint` + `@eslint/js`，
     没有 eslint-plugin-import**，所以连"幽灵依赖"都没人在跑。
   - **声明未用（P08）** 没有任何主流 eslint / tsc 规则管：`noUnusedLocals` 看文件内局部变量、
     `no-unused-vars` 看文件内声明与导入，**都不知道 package.json**；`no-extraneous-dependencies` 是反方向；
     `import/no-unused-modules` 说的是"模块没人引用"，与"依赖没人用"也不是一回事。真正的工具只有 knip / depcheck。

## 4. 判据的修订建议

`docs/DESIGN.md` §4.9 现在的判据是「纯语法 / 纯图属性、且不需要项目专有数据 → 委派」。
建议补两条，把"配置成本"和"漏掉的代价"纳入：

> **委派的三个条件（缺一不可）**：
> ① 纯语法 / 纯图属性，不需要项目专有数据；
> ② **宿主不写自定义配置就能生效**（否则那条约束实际等于没人管）；
> ③ 本体没有现成事实可直接判定（有的话自己判更稳，边际成本接近 0）。
>
> 委派之后仍然要能回答"它到底跑没跑"（R-51）。

> **顺带划清一个容易混的边界**：**文件内**的"声明了没用"（未使用的局部变量 / 导入）由
> `tsc --noUnusedLocals` 与 `@typescript-eslint/no-unused-vars` 管，而且**大概率是开的**
> （本仓 `strict` + `noUnusedLocals` + `noUnusedParameters` 都开着）—— 那一类**不在我们的委派清单里、也不用我们管**；
> 它属于 R-52（TS 严格度）想钉的"开关到底开没开"。**依赖层面**的"声明未用"是另一件事（见上）。

## 5. 建议动作（要你点头才动手）

| #     | 动作                                                                                                                                                                                                                                                | 代价                                                     | 收益                                  |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------- |
| **A** | **收回 P03 / P08**：幽灵依赖（P03）与声明了没用的依赖（P08）→ 本体实现（事实 `ctx.deps.phantom` / `unused` 早就算好，`--verify-deps` 一直在用）。**P08 是完全没有规则管**；P03 有 eslint-plugin-import 可顶，但要赌宿主装了它、并且显式开了那条规则 |
|       | 两条规则 + 夹具                                                                                                                                                                                                                                     | 补上一个现在**完全没人管**的缺口；P03 不再赌宿主装了插件 |
| **C** | **形态型兜底**：假异步 / 随机 / 硬编码地址 / 假数据（H07–H09）→ 本体实现，形态由项目声明（或走数据表 + `allowOwn` 放宽）                                                                                                                            | 两条规则 + 夹具 + 声明字段                               | 覆盖"要写 AST 选择器才有人管"的那一类 |
| **D** | **相对越级 `../`（S10）或 TODO（H04）挑一条**顺手收回                                                                                                                                                                                               | 各一条规则                                               | 极便宜，但生态也便宜 —— 优先级最低    |

**不建议动的**：`any` / 空 catch / console（开箱即用或一行配置，重写只会与生态重复）、
S08 / S15 / S16（本体已经在判，委派只是补充）。

**同时建议加一条门禁（就是 R-51）**：读宿主的 `devDependencies` 与 lint 链路，回答
"我们声明委派出去的那 N 条，到底有没有对应的工具在跑" —— 没有就明说"这 N 类零覆盖"。
没有它，这份评审的结论只能靠猜（G3 那一栏现在是空的）。

现方案要用户写什么 → 我们收回要付什么 → 收回后默认开还是默认关。

| #      | 委派项                                          | 现方案要用户写的配置（这就是"成本"）                                                                                                                                             | 收回成本                                                         | 建议默认                   | 漏掉的后果                                 |

### 已排除：C3（导入路径解析不到）—— **tsc 已经管了**

用户质疑："c3 ts 就会报错啊" —— 实测确认，**这条不需要收回**：

```
# 一个普通 TS 项目（moduleResolution: bundler + paths 别名），故意写错路径：
src/broken.ts(1,19): error TS2307: Cannot find module './missing' or its corresponding type declarations.
src/broken-alias.ts(1,19): error TS2307: Cannot find module '@/nope' or its corresponding type declarations.
→ tsc --noEmit 退出码 2（非零，CI 直接红）
```

**边界（也测了）**：`.js` 文件在 `allowJs: false` 时不在 tsc 程序内（`include` 不覆盖它时 tsc 甚至会报
TS18003「没有输入」），所以"文件类型与 tsconfig 射程之外"那一小块 tsc 管不到 ——
但那部分由**构建**兜（Vite / webpack 解析不到同样会失败），而且我们原来的实现（S33）**也只判契约内的文件**，
射程与 tsc 基本重合。**增量价值≈0，不值得一条规则** —— 这与 R-04 判"不做（委派）"、删掉 S33 的结论一致。

### 我的推荐组合

- **必收（零成本 + 现在完全没人管）**：**C1 + C2** —— 事实已经算好，只差两条规则与夹具。
- **划算（我们已有扫描器，用户却要写几十行配置）**：**C4 + C6**（C5 顺手）。
- **值得但要设计**：**C7**（形态由项目声明，避免误伤）；**C8** 要先定"字符串 ≠ 文案"的边界再动。
- **可选**：**C9**（极便宜，但生态也便宜）。**C3 已排除**（见上：tsc 会报 TS2307）。

> 勾选方式：说编号即可（例如"C1 C2 C4"）。每一条都会按流程走「需求落盘 → 设计 → 规格 → 夹具 + 单测 → 双 Node 门禁」。
