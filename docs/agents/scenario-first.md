# 需求只讲场景

**约定：对需求，先讲场景，不讲规则。**

规则是**解法的形状**，场景才是**疼**。先摆规则，等于让人在别人的解法里做选择题 ——
容易做出"判据漂亮但没人疼"的门禁，也看不出到底该不该做。本仓的门禁价值只有一个：
**拦住真会发生的坏结果**（比如 §6.1 里那条"覆盖率一直在跑，但统计的是错的进程"）。
所以顺序永远是：**场景对齐 → 决定做不做 → 才谈判据与误伤**。

**清单在哪**：需求的全貌与状态在根目录 `REQUIREMENTS.md`（唯一来源）—— 每条 = 痛点 + 预期行为 + 状态。
新需求先写进那里，再开工；对话里只讨论场景，不直接改需求清单。

## 场景怎么写（四问）

一条场景至少能回答这四问：

1. **谁在什么时候会疼** —— 换库 / 上生产 / 重构删码 / 多人协作 / 发版给下游
2. **具体长什么样** —— 贴得出代码或文件形态，一句话能被人复述
3. **现在拦不拦得住** —— 会报 / 不会报 / 只覆盖一半（**这条必须自己先验过**，别猜）
4. **漏掉的后果** —— 越权入口、首屏 1.2MB、脏缓存查一下午、全仓 grep、迁移永远做不完

## 正例 / 反例

> ✗ 「加一条规则：`data-layer` 面声明 `fetchApis` / `fetchIn`，判 `facts.calls` 的 callee 落在哪个 glob」

> ✓ 「**页面里直接 `useQuery`、域里直接 `fetch('/api/x')`** —— 换数据层要翻遍页面，
> 契约类型散在十几个域里，写测试必须 mock 网络。**现在不报。**」
>
> ✓ 「**重构后 `CrewsPage.old.tsx` 留在 `views/`** —— 两年后没人敢删，新人抄了旧的那份，
> 两套实现行为不一致。**现在不报**（它在 `views/` 下，角色判定上是合法页面）。」

## 什么时候可以讲规则

- 被明确要求时；
- 场景对齐之后，讨论"判到什么程度 / 会误伤哪些正常写法"时；
- **落地记录里照旧写规则**（`spec.md` / `CHANGELOG.md` / `DESIGN.md`）——
  文档是解法的家，对话是场景的家，两者不要互相顶替。

## 对写需求的人的反向约束

`spec.md` 的「场景」一节**写不出真实场景的需求，先不做**（`docs/agents/spec-template.md`）。
这不是流程洁癖：本仓已实现的门禁里，凡是当初从"我觉得该判"出发的那几条，
最后要么被委派出去，要么写了 `[]` / 默认关的空转开关 —— 从场景出发的那些全都留下来了。
