# 开发流程：需求 → 设计 → 落地

> 本仓只走一条主线：**从实际场景切入 → 先落盘需求 → 再落盘设计 → 最后落地**。
> 每一步都有**产物**（写到对应文档，不许只活在对话里）与**准入门禁**（不满足就别往下走）。
> 这份约定本身**可判定**：`tests/process.test.mjs` 会查活跃规格有没有场景与需求编号、
> 设计文档里的规则数 / 夹具数与实际是否一致 —— 流程不靠自觉。

## 主线（五步）

```
① 场景     谁在什么时候会疼？现在拦不拦得住？漏掉的后果是什么？
   └ 落盘 → REQUIREMENTS.md（R-xx：痛点带例子 / 期望行为 / 状态 / 交给谁）
② 取舍     做不做？做到什么程度？会误伤哪些正常写法？—— 先定口味，再谈实现
   └ 落盘 → REQUIREMENTS.md 的状态（未开始 / 需定口味 / 待定）+ spec「边界与取舍」
③ 设计     判据落在 L1–L3？用哪个机制（AST / 图 / CSS / 路径 / 调用）？会漏什么？
   └ 落盘 → docs/DESIGN.md（规则行与协议）· 分层或模块职责变了 → docs/ARCHITECTURE.md · 重要取舍 → docs/adr/
④ 规格     这条需求的最小验收是什么？跑什么命令、期望什么结果？
   └ 落盘 → .scratch/<slug>/spec.md（Status + 场景 + 目标 + 非目标 + 验收 + 边界 + Comments）
⑤ 落地     代码 + 夹具（违规必报 × 合规不报）+ 测试 + 文档同步 + 门禁
   └ 落盘 → 代码 / __fixtures__ / tests / CHANGELOG / README 进度 / DESIGN 规则表
```

每走完一步，把 spec 的 `Status` 往前推：`draft → ready-for-agent → in-progress → done`。

## 每步的准入与产物

| 步     | 准入（不满足就别往下）                                               | 产物                                      | 谁来判        |
| ------ | -------------------------------------------------------------------- | ----------------------------------------- | ------------- |
| ① 场景 | 说得清「谁在什么时候会疼」，而且**自己验过**现在拦不拦得住（不许猜） | REQUIREMENTS 一条（带具体例子）           | 提需求的人    |
| ② 取舍 | 明确「做 / 不做 / 待定」；要拍板的点写明（阈值多少、允许哪些写法）   | REQUIREMENTS 状态 + spec 的「边界与取舍」 | 提需求的人    |
| ③ 设计 | 判定等级在 L1–L3；机制与边界写清（会漏什么、会误伤谁）               | DESIGN（+ ARCHITECTURE / adr）            | 设计 + review |
| ④ 规格 | spec 有「场景」且**验收可被命令判定**                                | `.scratch/<slug>/spec.md`                 | 写规格的人    |
| ⑤ 落地 | 夹具齐、测试过、`pnpm check` 双 Node 绿、文档同步                    | 代码 + 夹具 + 测试 + CHANGELOG            | `pnpm check`  |

## 三条硬规矩

1. **需求不落盘，不开工**：只在对话里说过的需求，先写进 `REQUIREMENTS.md`；写不出真实场景的先不做。
2. **设计不落盘，不写代码**：判据、边界、误伤面先进 `docs/DESIGN.md`（架构性变更进 `docs/ARCHITECTURE.md`）；
   代码只是把设计翻译一遍。
3. **落地没有夹具 = 没落地**：每条规则一对「违规必报 × 合规不报」，夹具 `exact`（多报也算错）。

## 允许的例外（别让流程变官僚）

| 情况                       | 怎么走                                                                                        |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| 修 bug / 改措辞 / 补测试   | 可以直接改 + CHANGELOG；但**行为变了**（谁报、报什么、不报什么）要回填 REQUIREMENTS 与 DESIGN |
| 纯文档整理                 | 直接改，过 `--check-docs` 与一致性门禁                                                        |
| 口径撤销（某条需求不做了） | 改 REQUIREMENTS 的状态 + CHANGELOG 记一笔；spec 追加 Comment，**不删历史**                    |
| 紧急修复（线上红了）       | 先修，一次提交里补上 REQUIREMENTS / DESIGN 回填；回填不许拖到"以后"                           |

## 流程自己被谁检查

| 检查                                | 在哪                     | 判什么                                                  |
| ----------------------------------- | ------------------------ | ------------------------------------------------------- |
| 活跃规格有 Status / 场景 / 需求编号 | `tests/process.test.mjs` | 未完成的活必须有场景与需求锚点（`done` 的历史规格不查） |
| 需求编号连续、不重复                | 同上                     | `R-xx` 不复用、不跳号                                   |
| 设计文档的规则数 / 夹具数与实际一致 | 同上                     | 加了规则不改 DESIGN / README = **设计没落盘**           |
| 文档管理块与配置一致                | `--check-docs`           | 人读文档与机读配置同源                                  |
| 每条规则有夹具                      | `--self-test` + 覆盖测试 | 「没有夹具的规则等于没有规则」                          |

## 反例（这套流程要防的四种走法）

| 反例                   | 会怎样                                         | 正确走法                                 |
| ---------------------- | ---------------------------------------------- | ---------------------------------------- |
| 对话里定完直接写代码   | 三周后没人记得为什么这么判；需求与实现两处漂移 | 先落 `REQUIREMENTS.md` 一条              |
| 先写规则再去找场景     | 判据漂亮但没人疼，最后留个默认关的空转开关     | 场景先行（见 `scenario-first.md`）       |
| 设计只在 spec 里写一句 | 后来的规则互相打架 —— 没人知道边界在哪         | 判据与边界进 DESIGN，spec 只写这条的规格 |
| 代码先合、文档"以后补" | 以后不会补。一致性门禁就是为这条反例存在的     | 同一次提交里同步                         |
