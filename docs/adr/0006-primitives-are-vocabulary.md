# 检测原语是分类词汇，不是运行时层

`PARADIGM.md` §3 的十个检测原语（`forbidDependency` / `mustReference` / `exclusiveOwner` …）**只用于给规则分类**：
每条规则都能说清自己是哪个（或哪几个）原语的实例，于是「不为每个项目另写一套」有共同语言可讲。
**本体里没有 `primitives` 模块，也没有原语 DSL** —— 规则是「对事实模型的纯函数」，直接消费 facts / graph / tokens。

三条理由拒绝把它做成运行时层：

1. **没有消费者**：把十个名字变成代码，只会有一个人为的抽象层；规则该写的判据一条不少。本范式自己禁止
   「声明了没人读的配置」—— 同一条理由适用于"造一层没人真正消费的抽象"。
2. **会重新引入可判定性论证的负担**：原语一旦成为可执行 DSL（尤其带回调/嵌套组合），就必须重新证明
   它产出的判定仍然只落在 L1–L3。而现在的形状（纯函数读事实模型）已经把这件事做到了：
   `createRule()` 在定义期就拒绝 `error + L4/L5`。
3. **会挡住换 parser**：现在的边界是「parser 产 facts、规则不碰 AST」。多一层原语只会在这条边界上再加一环。

保证来自两个**可机检**的锚点，而不是来自"有分类"：

| 锚点                             | 强制方式                                                         |
| -------------------------------- | ---------------------------------------------------------------- |
| 规则 id ↔ 域、`error` 只落 L1–L3 | `createRule()` 定义期抛错（`src/engine/rule.ts`）                |
| 每条规则「违规必报 × 合规不报」  | `--self-test` 跑 `__fixtures__/`（本仓 55 条规则 / 55 条全覆盖） |

## Considered Options

- **实现一个 `primitives` 模块（每个原语一个函数，规则调用它们）** —— 拒绝。它不减少任何判据，只增加一层
  需要自己证明「仍落 L1–L3」的抽象；且与「声明必须有消费者」相冲突（没有规则会因为没有它而写不出来）。
- **实现成可执行 DSL（配置里声明原语组合）** —— 拒绝。等于让配置携带逻辑，直接违反 ADR-0002（适配器是数据，
  不是插件）与"用户只填数据"的边界，判定等级也随之失去保证。
- **删掉这张表，只留规则清单** —— 拒绝。分类词汇有实际用处：它让"该不该加一条新规则、还是复用已有形态"
  这个问题有共同语言，也让审查者能一眼看出某条规则属于哪类判据。

## Consequences

- 文档里提到原语时，一律写成**分类词汇**，不得暗示存在原语引擎/DSL（PARADIGM §3.1 已写明）。
- 新增规则时**不需要**先"注册原语"：写规则 + 加一对夹具即可。
- 若将来真要把某个原语做成可复用实现（例如 `mustReference` 的通用匹配器），判据是：
  **至少两条规则共用它**，且它本身还能被夹具证伪。届时应连同 `requires` 一起加，而不是先造层后找理由。
