# ADR-0007 域有两个公开面：`routes.tsx`（路由挂载）与 `index.ts`（业务公开面）

- **状态**：已采纳（2026-09-25）—— **取代** `PARADIGM.md` §6.3 里"域只有一个公开面"的旧论证
- **关联**：R-98 · 架构审查 [`C1 / C2`](../../.scratch/arch-review/review.md)（两份独立逐文件审查都指向这里）

## 背景

旧论证（写在 PARADIGM §6.3）：域只留 `routes.tsx` 一个公开面，`views/` 对外私有 → **深模块**，
改内部实现不影响调用方；域间零依赖，跨域组合一律"提升到 `shared` 或 `app`"。
当时明确**否掉**了"给域开第二个公开面 `index.ts`"，理由是"深模块变成两个出口，边界从内部开始漏"。

实测（架构审查，照抄到 10 倍规模）：

1. **跨域协作没有合法通道**：`isolate: ['domain']` 禁同层互引，S04/S05/S23 又只认 `routes.tsx`，
   于是"B 域要用 A 域的东西"唯一的出路是把东西**抬进 `shared`**。
2. **shared 因此长成"第二套 modules"**：端点 / DTO / 缓存键 / 请求策略 / 分页常量全集中在
   `shared/api` 与 `shared/config` —— 50 个域时那是 5 条横向 merge 队列，下线一个域要跨 6 处删。
3. 两份**互相独立**的审查（canonical / FSD）得出同一结论：问题不在域的写法，在**没有出口**。

## 决策

1. **域可以有两个入口角色**（都带 `entry: true`）：`routes.tsx`（给 `app` 挂路由）与
   `index.ts`（**业务公开面**：实体 / 工具 / 类型，给别的域用）。
2. **公开面判定改成声明驱动**：S04 / S05 以前只读路由适配器的 `routeFiles`（`routes.tsx`），
   现在认**所有 `entry: true` 的角色** —— 与 S23 早就用的口径一致（S23 一直是声明驱动的）。
3. **声明上二选一**（`structure.*`）：
   - `publicApi: ['domain']`（**推荐**）：跨域只许经入口，直捣内部照报；
   - `isolate: ['domain']`：同层互引一律禁 —— 那时跨域只能靠 `app` 组装或抬进 `shared`。

## 后果

- **好处**：跨域协作有了一条**可判定的合法通道**；`shared` 回到"真正跨域中立"的位置；
  域的导出面是**显式**的（`index.ts` 里写什么，别域就能用什么）。
- **代价（旧论证仍然成立的部分）**：域从"一个门"变成"两个门"，深模块的纯度下降。
  因此约定：`index.ts` **只导出实体 / 工具 / 类型**，不导出实现细节；页面仍然不外借（`views/` 依旧私有）。
- **何时仍该用 `isolate`**：域之间本来就该零协作、或跨域组合应当显式上提到 `app` 的项目。
- **对规则的影响**：`S04` / `S05` 的判据从"路由适配器的词汇"变成"角色表的 `entry` 标记"；
  两者都是**数据**，所以换范式（FSD 的 `index.ts` 就是入口）时同一套规则继续成立。
