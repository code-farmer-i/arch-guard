# 依赖白名单必须显式开启（能力表不等于批准清单）

`deps()` 里两张表职责分离：**能力表**（`capabilities`）回答「这个能力必须用哪个方案」，只驱动 `P06`；**批准清单**（`allow`）回答「这个项目的运行时依赖集合是哪几个」，`P01` 只在 `allow` 非空时进入 fail-closed。

旧实现是 `approved = allow ∪ capabilities.values`，且以 `approved.size === 0` 判空。后果是「只想限定日期格式化必须用 dayjs」写成 `deps({ capabilities: { datetime: 'dayjs' } })` 时，等价于宣布**批准清单里只有 dayjs** —— 项目里 react / react-dom / antd 全部报 `P01 未登记的运行时依赖`。用户要的是选型声明，拿到的却是一张几乎为空的白名单。

三条理由：

1. **语义过载**：一张表同时承担「选型声明」与「审批清单」两种意思，且两种意思的默认值相反（前者默认空=不约束，后者空=全拒）。
2. **那个 union 本来就是冗余**：`policyConflicts` 已经要求「只要 `allow` 非空，每个能力的首选库必须在 `allow` 里」，否则引擎直接抛错。能力首选不可能只存在于 capabilities 里 —— union 唯一能观察到的效果，就是打开 P01。
3. **违背本仓自己的原则**：「不许默默按某一侧生效」（`run.ts` 里 `policyConflicts` 的注释）。隐式开启一条 error 级红线，是比配置冲突更隐蔽的形态。

## Considered Options

- **保持现状，只在文档里写清楚** —— 拒绝。等于要求「只想声明选型」的用户先去把全部运行时依赖抄一遍；这正是实际使用中卡住的地方。
- **新增 `allowlist: 'strict' | 'off'` 开关** —— 拒绝。多一个只表达「`allow` 是否为空」的字段，等于把同一件事写成两处。
- **要求能力表里的首选库必须出现在 `allow`，同时保留隐式开启** —— 自相矛盾：没有 `allow` 就没有对照物。

## Consequences

- 只配 `capabilities` 的项目**不再**获得 `P01`；要「未登记即拒」必须显式写 `deps({ allow: [...] })`。能力首选仍可只登记一次（写进 `allow` 即可，`policyConflicts` 会核对）。
- 批准名单的**组成**是 `allow ∪ 适配表声明的 packages`。适配器本来就是「项目用什么库」的唯一声明（P04 读同一份数据），没理由让组件库在 `allow` 里重抄一遍；但它只**并入名单**，不负责打开 `P01` —— 开关仍然只有 `allow`，否则重演这条 ADR 要修的同一个坑。
- 这是一次**收紧方向反转**的行为变更：原本靠能力表隐式获得 `P01` 的存量配置会失去这条门禁。因此**不静默**：`runGuard` 在「有 `capabilities`、无 `allow`」时打印 notice，说明能力表只驱动 P06、P01 未开启。
- 配置**格式**没变（字段与类型不变），故不 bump `CONFIG_SPEC_VERSION`；语义变更记入 CHANGELOG。若将来需要硬拦截存量配置，再把 `specVersion` 提到 `2` 即可 —— 通道保留，不在本次使用。
