# 架构审查：两份「完整配置」样板

> 审查对象：`examples/full/`（`canonical()` 三根拓扑）与 `examples/full-fsd/`（`fsd()` 六层切片）。
> 方法：① 结构度量（角色分布 / 层间边 / 扇入）② 演进成本实测（改一处要动几个文件）
> ③ 盲区实测（拿真实世界会出的问题撞门禁，看哪些**没人管**）④ 两份逐文件审查（按维度出 finding）。
> **只读审查**，不改示例；结论要落地的部分才写成需求（`REQUIREMENTS.md`）。

---

## 1. 结构度量

| 度量 | canonical（`full`） | FSD（`full-fsd`） |
| --- | --- | --- |
| 源文件 | 61 | 60 |
| 角色种数 | 21 | 30 |
| index / 公开面文件 | 5（导出名共 9） | **19**（导出名共 35） |
| 最高的扇入文件 | `shared/config/paths.ts`(6) | `shared/config/index.ts`(4) |
| 层间边（主要） | `app→modules` `modules→shared` `app→shared` | `app→pages/widgets` `pages→features/entities/shared` `features/entities→shared` |
| 反方向边 | 0 | 0 |

**读法**：两套都是"单向、无反向依赖"的健康形状 ✓。差异来自范式：FSD 的公开面是**规范要求**（每个切片一个 `index.ts`），
所以 index 文件多 4 倍、导出名多 4 倍 —— 这是**规范的成本**，不是我们的设计问题；代价是"每个切片都要维护一个公开面"。

## 2. 演进成本实测（同一类改动要动几个文件）

| 改动 | canonical | FSD | 说明 |
| --- | --- | --- | --- |
| 换缓存键前缀 | **1 个文件** | **1 个文件** | `shared/api/queryKeys.ts` ✓ 唯一出处生效 |
| 换 UI 组件库 | **0 个文件直接引 antd** | 同 | 组件一律经 `shared/components/ui`（canonical）/ `shared/ui/<child>`（FSD）✓ |
| 换环境变量名 | **1 个文件** | 同 | `shared/config/env.ts`（S44 落点）✓ |
| 换埋点事件名 | **1 个文件** | 同 | `shared/lib/analytics/events.ts`（D24 落点）✓ |
| **域 / 切片改名**（`crews`→`teams`） | **12 个文件** | **12 个** | 见下 |

**改名 12 个文件的成分**（canonical）：

```
目录/导入路径（机械改动）        3 个   app/router · modules/crews/routes · modules/crews/views
生成物（重新生成，不该手改）      1 个   shared/api/generated/crews.gen.ts
路由路径（语义，要改）            1 个   shared/config/paths.ts
缓存键（语义，要改）              1 个   shared/api/queryKeys.ts
i18n 命名空间（语义，要改）       2 个   locales/{zh-CN,en}/index.ts
埋点事件名（**外部数据契约**）     2 个   lib/analytics/{events,index}.ts
后端端点（**外部契约**）          1 个   shared/api/client.ts
测试断言引用                      1 个   shared/lib/storage.test.ts
```

**结论**：12 不是"耦合"，而是"同一个词跨了 5 层语义"（目录名 / 前端路由 / 后端端点 / 缓存键 / 埋点事件名）。
好消息是**每一层都各自只有一处**（外部契约的那两个都在单文件里）—— 也就是说，改名时**每一处都要人做一次判断**，
而不是"改一处漏三处"。这是"唯一出处"架构该有的样子。**但**：`/crews` 同时是**前端路由**（`paths.ts`）与
**后端端点**（`client.ts`）的值 —— 值相同、语义不同，读者容易以为它们是一件事（改路由会以为改了接口）。

## 3. 盲区实测：这三类问题今天**没人管**

拿真实世界会出的问题去撞门禁（`full` 副本，改完跑 `node es/cli.js`）：

| 撞的问题 | 结果 | 判定 |
| --- | --- | --- |
| **后端端点第二个出处**（另一个文件里再拼一次 `` `${API_BASE_URL}/crews` ``） | **不报**（只报了撞进去的 S13/S18） | ✗ **真空白**：端点没有"唯一出处"受体，改接口时漏一处 = 404 |
| **缓存键形状漂移**（`detail: ['crews','detail',id]` 而 `list: ['crews']`） | **不报** | ✗ **真空白**：`invalidateQueries(['crews'])` 前缀不匹配 → **缓存不失效、数据不刷新** |
| **同一份状态两处持有**（页面里再 `useState(selected)` 拷一份 store 的值） | **不报** | ✗ 空白，但判据偏形态 —— 需要真实场景才好定 |

另外核了规则家族：**98 条 = 结构 42 · 设计 25 · 文案 7 · 依赖 10 · 度量 8 · 反退化 6**，
**没有任何一条**碰 endpoint；也**没有**碰 loading / error 态。

## 4. 两份示例的「非范式强制」差异（需要明文对照，否则"抄哪个"取决于你打开哪个）

| 维度 | canonical | FSD | 是范式强制吗 |
| --- | --- | --- | --- |
| 取数落点 | `modules/<域>/hooks/use*.ts`（**域持有**） | `pages/<切片>/api/use*.ts`（**页面持有**） | **不是** —— 两种都合法，但复用时成本不同 |
| 页面导出形态 | 默认导出（S13 要求） | 命名导出 + index 公开面 | 是（槽位语义 vs 公开面语义） |
| 客户端状态 | `shared/stores/shell.ts`（S41 专用槽位） | `shared/lib/shell/{index,store}.ts` | 是（FSD 的 shared 没有 stores 段） |
| 共享组件形态 | `shared/components/ui/AppButton.tsx` + css | `shared/ui/app-button/{index,Comp.tsx,Comp.module.css}` | 是 |
| 样式令牌 | `shared/styles/{tokens,vendor}` | `app/styles/{tokens,vendor}` | 是（官方 app 有 styles 段） |
| 公开面数量 | 5 个 index | 19 个 index | 是（FSD 规范要求切片公开面） |

**结论**：唯一"范式没规定、但我们两套示例给了不同答案"的是**取数落点**（域/实体持有 vs 页面持有）。
页面持有在"该数据被多个页面用"时必然要重构；域/实体持有从一开始就能复用。这条要么统一，要么写进 `PARADIGM.md` 说清取舍。

## 6. 结论：架构哪些成立、哪些要改

**成立（可以被真实项目照抄的部分）**

1. **单向依赖 + 无反向边**：两套都是 0 条反方向边 —— 这是"可判定不变量"最值钱的那一条。
2. **唯一出处真的起作用**：5 个可测面里 4 个都是"改 1 个文件"（缓存键 / 组件库 / 环境变量 / 事件名）。
3. **跨切片/跨域一律走公开面**：FSD 19 个 index、canonical 5 个 index，且无一处绕过。
4. **外部契约各自单点**：后端端点只在 `api/client.ts`、埋点事件名只在 `events.ts` —— 改名时这两处**必须人判断**（这是对的，它们是外部契约）。
5. **范式差异都有官方依据**：样式落点（R-96 刚修）、布局进 widgets、切片公开面，逐条能对着官方 v2.1 说清。

**要改**

1. **取数落点两套不一致**（非范式强制）→ 需要明文建议。
2. **后端端点缺"唯一出处"受体**（实测盲区）→ 该开发。
3. **缓存键形状缺一致性判据**（实测盲区，直接对应"缓存不失效"事故）→ 该开发。
4. **`queryKeyFrom` 是单值**：想"键跟着模块走"表达不了 → 该扩展。
5. **FSD `@x` 未实现**：官方一等公民，今天用会被误报 S01 → 该开发或文档明说。
6. **配置入口缺失**：5 行能跑但没人这么教（报告只说"停用了 29 条"，不说"补哪一行"）→ 该开发。

## 7. 从这份架构倒推的「待开发」清单（候选，等确认）

按"证据强度 × 收益"排序；每条都注了证据来源。

**先验可行性**（dump 事实模型，避免"写条规则"变成空话）：

```
src/shared/api/queryKeys.ts 的 facts.strings：
  {value:'crews',  prop:'list'}      ← list: ['crews']  ✓ 属性名在
  {value:'crews',  prop:null}        ← detail: (id) => ['crews', id]  ✗ 箭头函数体里 prop 丢了
src/shared/api/client.ts：
  calls: [{callee:'fetch', line:6}]  ← **stringArg / keyPrefix 都没有**
  strings: 只有数据里的 'crews'/'orders'，**端点 `/crews?limit=` 根本不在事实里**
```

原因：端点写成模板串 `` `${API_BASE_URL}/crews?limit=${limit}` ``，而模板串的**静态前缀是空的**
（开头就是插值），现有 `keyPrefix` 机制只在"前导静态段非空"时记；`facts.strings` 只收**纯字符串字面量**。
→ 所以"端点唯一出处"今天**判不了**：端点在事实模型里**是隐形的**。

| # | 候选 | 证据 | 可行性 / 前置工作 |
| --- | --- | --- | --- |
| 1 | **后端端点唯一出处**：新增受体（`endpoints({ from })`）+ 规则 | §3 实测盲区 | **需先扩事实模型**：记录每次调用的**实参形态**（纯字面量 / 模板静态段 / 标识符）——
模板可以只记「静态段数组」`['', '/crews?limit=', '']`；有了它，"端点字面量只许出现在端点表"就变成可判定 |
| 2 | **缓存键形状一致**：同一 key 文件里所有键数组必须以同一前缀开头 | §3 实测盲区（`invalidate` 不失效） | **需先扩事实模型**：数组首元素要带上**所属导出/属性路径**（现在箭头函数体里的 `prop` 是 null），
才能按"每个 key 工厂对象"分组比前缀（`crewKeys` 用 `crews`、`orderKeys` 用 `orders` 是合法的，不能全局比） |
| 3 | **`queryKeyFrom` 支持多落点**：键可以跟着模块/切片走 | 用户提问 | 能力扩展 |
| 4 | **`@x` 跨引用公开面** | 官方规范 + 现有误报 | 规范对齐 |
| 5 | **配置入口三件**：报告告诉你"补哪一行" / 报告给可复制片段 / `init` 生成器 | 用户提问"用户会配吗" | UX |
| 6 | **取数落点的明文建议**（域/实体持有 vs 页面持有） | §4 两套不一致 | 文档/规范 |
| 7 | **`canonical()` 补齐 structure 默认**（对齐 `fsd()`） | 用户上次未选（Tier-2） | 预设默认 |
| 8 | **状态归属**：组件直接读全局 store / 同一状态两处持有 | §3 空白 | 待定（判据偏形态） |

**明确不做（建议写进 `REQUIREMENTS.md` §八 的理由）**：
loading / error 态、DTO ↔ 领域模型的映射、错误被吞掉 —— 这些形态自由度大、判据不稳，
判了就是误报（与 N-09 / N-11 / N-12 同一类判断）。
