# 组耦合上限（上帝域 / 上帝模块）

Status: in-progress

## 场景（对应 REQUIREMENTS.md 的 R-44）

- **改一个签名动全仓时**：`crews`、`orders`、`users` 三个域都在
  `import { CrewCard } from '@/modules/crews/components/CrewCard'` —— 想动 `crews` 的一个 props，
  得同时改三个域，谁都不敢动。**现在：不报**。
- **拆不动时**：某个域把订单、用户、报表的事都碰一点（fan-out 高），想把它拆成两个，
  却发现每个方向都有人依赖它。**现在：不报**。
- **"文件级"和"域级"的差距**：S34 只能看**单个文件**被几十处引用（神模块），
  看不见"整个域被一半的域依赖"这种**架构级**的耦合。**现在：不报**。

## 目标

- 项目声明上限后，**域（或任意组维度）的外部耦合**超限即报：
  - **fan-in**：有多少个**其它组**依赖这个组（被依赖过多 = 上帝域）
  - **fan-out**：这个组依赖了多少个**其它组**（什么都碰 = 职责不清）
- 只数**项目内**的跨组边（同组内部的文件互引不算耦合）。
- 阈值与维度都由项目声明（`dimension` + `maxFanIn` / `maxFanOut` 至少给一个）—— **没声明不判**。
- 报告点名"它是谁、被多少个组依赖、都是谁"，锚在**参与度最高的那个文件**上（可点开就改）。

## 非目标

- 不判"这个域该不该拆"（L5）。本规则只把"耦合度"变成可见的数字。
- 不算包依赖（那是 M07 `depsBudget`）、不算文件级度数（那已是 S34）。
- 不做"环状依赖"（S08）与"死切片"（S28）—— 那两条分别管可达性与**下限**，这条只加上限。

## 验收标准

- 夹具 `coupling-limits`（违规必报 × 合规不报）：声明 `{ dimension: 'domain', maxFanIn: 2, maxFanOut: 2 }`，
  被三个域依赖的域、依赖三个域的域各报一条；只被一个域依赖的域**不报**。
- 单测：未声明维度 → 不报；`maxFanIn` 未超 → 不报；同组内部互引**不计入**；声明里
  `maxIn`/`maxOut` 都不给 → 解析配置时直接报错（"这条声明什么都没说"）。
- 双 Node `pnpm check` EXIT=0；DESIGN §5.1 有 S39 行、规则数与夹具数口径同步。

## 边界与取舍

- **只数直接边**：A→B→C 里 A 不"耦合" C。间接耦合要做可达性聚合，噪音大且难解释；
  真要收紧，靠声明更小的阈值即可。
- **`dimension` 用捕获名**（`domain` / `slice` / 自定义）：与 S22/S23/S26/S28 同一套词汇，
  所以 FSD 与 canonical 都能用同一条规则；捕获值取不到（角色表没这个捕获）→ 不报。
- **测试角色（layer ≥ 90）不参与**：`**/*.test.*` 天然引用各处，算进去只会让所有域都超限。
- **点名的"参与度最高的文件"** 是启发式：只用来决定锚点，不参与判定（判定只看"多少个组"）。
- **被否方案**：把上限做成默认值（不声明也判 8 个组）—— 各项目规模差太多，
  猜出来的阈值会把正常项目报红；与"声明了才判"的纪律也相反。
