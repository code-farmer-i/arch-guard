# 规格：架构加固批次（B1–B12 + A1–A14）

> 需求编号：**R-97 – R-108**（本体能力/规则）+ 示例重构 A 类（`modules/<域>` 与 `entities/<切片>` 的形态，
> 由 R-97/R-98 的期望与本文档的 A 清单共同约束）。
> 判不做的 4 项：`REQUIREMENTS.md` §八 **N-14 – N-17**。
> 依据：`.scratch/arch-review/review.md`（架构审查：度量 + 演进成本 + 盲区实测 + 覆盖图 + 两份逐文件审查）。

## 场景

团队照抄 `examples/full`（canonical）或 `examples/full-fsd`（FSD）以后长到 10 倍体量，会发生这些事：

1. **每加一个域都要改 shared**：端点 / DTO / 缓存键 / 请求策略 / 分页常量全在 `shared/api` 与 `shared/config`，
   域本身只剩"读取壳"。50 个域时这 5 个文件是 5 条横向 merge 队列，下线一个域要跨 6 处删。
2. **域之间没有合法的协作通道**：canonical 的域公开面只有 `routes.tsx`（路由入口），
   `isolate: ['domain']` 禁直连、S23 禁绕过入口 —— 想共享实体只能"抬进 shared"，把病灶喂大。
3. **两类"假绿"**：① `import { crewPolicy } from '@/shared/api/client'` 里的 `crewPolicy` 根本不存在
   （示例里真发生 4 处）② 示例唯一的测试 import 了不存在的常量，坏了很久没人知道（门禁从不跑示例测试）。
4. **门禁绿但跑起来是坏的**：四份全局 CSS 没有任何入口（主题静默不生效）；主按钮白字橙底 3.1:1，
   而 `contrastPairs` 只声明了必然通过的那一对。
5. **会真实发错的缺陷**：埋点在组件体里直接调（每次重渲染都上报）；缓存键带参而请求不带参（筛选必然错）；
   键形状漂移（`invalidate` 前缀不匹配 → 缓存不失效）；参数化路由只能写成模板串（D23 看不见）。

目标：把上面每一类都变成**可判定的不变量**（本体）+ **照抄不会长歪的形状**（示例）。

## 每条需求的验收（统一）

1. **需求先落盘**：`REQUIREMENTS.md` 有该条（状态从 `进行中` → `已完成`，小结数字同步）。
2. **实现 + 夹具**：新规则必须有「违规必报 × 合规不报」夹具（`__fixtures__/`，`exact`），
   并补齐针对性的单测；能力扩展必须改「能力协商」相关测试。
3. **文档同步**：`docs/DESIGN.md`（规则表 / 实现清单 / 判定等级）、`docs/ARCHITECTURE.md`（规则数与夹具数）、
   `README.md`（规则数）、`docs/USAGE.md`（用法）、`CHANGELOG.md`（含迁移说明）。
4. **门禁**：`pnpm check`（Node 24）`EXIT=0`；示例仍是 0 finding；示例自带测试也跑（`examples:test`）。
5. **提交**：一条需求（或一个紧密批次）一个提交，提交信息写清"改了什么 + 证据"。
